# Memory measurements

The diagnostic and the composed Fieldnote validation answer different questions. The diagnostic measures shared attention storage and useful parallel work with fixed inputs. The composed run exercises the actual Fieldnote UI and compatible hosts, including preflight, original PDF/image uploads, reranking, reports, synthesis and continuation. Diagnostic results alone do not establish a whole-application memory advantage.

## Run

From the lloyal-bench directory:

```sh
npm run bench -- memory doctor
npm run bench -- memory run --protocol protocols/memory-v1.json --rounds 1 --output comparisons/my-agent-count
npm run bench -- memory analyze --experiment comparisons/my-agent-count
.venv-plots/bin/python scripts/plot_memory.py comparisons/my-agent-count
```

The default protocol requests 1, 2, 4 and 8 siblings, three fresh-process repeats, a shared 96-record ledger, a 32,768-cell context and 16 sequence slots on both paths. Every response is generated by the model and checked against the frozen ledger. Native code uses root-package `withSpine`, `agentPool` and `parallel`; HTTP uses `StateGraph`, `Send` and `ChatOpenAI`. No mocked inference or private HDK methods.

For the separate cached-round experiment, pass `--rounds 2 --scope-rounds`. Each native round then uses the public Effection `scoped` operation inside the existing shared spine; HTTP continues to use ordinary graph invocations. The second round submits the same lookup requests again in the same model process. The raw HTTP timing receipts distinguish processed and cached tokens. A stable shared system message already provides a shared-prefix layout here, so the ordinary and shared-prefix HTTP arms coincide. There is no invented third control.

An eight-agent, two-round canary exposed retention of completed native schema-output branches until the outer Effection scope exits. `pruneOnReturn` only affected terminal-tool returns in the inspected implementation; it did not release these free-text JSON outputs. Those failed attempts remain in `comparisons/memory-sweep-2026-10-09` and `comparisons/memory-release-canary-2026-10-09`. Do not describe a successful first round as a successful two-round journey. The actual Fieldnote harness is unchanged.

Other controls:

```sh
# Telemetry-enabled and disabled runs, from the same binaries.
npm run bench -- memory run --counts 2 --repeats 2 --rounds 1 --overhead-check --output comparisons/my-overhead

# Predetermined capacity ladder; retain all failures.
npm run bench -- memory run --counts 8 --contexts 4096,8192,16384,32768 --rounds 1 --repeats 3 --continue-on-failure --output comparisons/my-capacity

# Resume using the same arguments plus --resume. Completed outcomes, including
# failures, are retained. Interrupted attempts receive a fresh process/directory.
```

The whole-run worker timeout is 420 seconds, and HTTP requests have a 300-second timeout. This is not a latency service-level objective. A capacity headline needs a separately declared completion-time target, successful output checks, repeated boundary conditions and complete allocation ownership. The current diagnostic does not silently turn a timeout into a memory failure.

## Actual Fieldnote UI

```sh
./start.command fieldnote --instrumented --port 8100 --corpus fixtures/generated/corpus
# Stop it before starting the other stack.
./start.command langgraph --instrumented --port 8100 --corpus fixtures/generated/corpus

# Automated UI journey, both stacks sequentially, fresh app data/coverage.
npm run bench -- memory composed --output comparisons/my-composed
```

`memory composed` uses Playwright and the actual shared UI. It uploads the original files, selects Survey/Standard, edits through the plan controls, and observes the existing browser WebSocket. It never opens a second native session or injects protocol commands. The driver checks planner routing before assigning the four frozen objectives: three corpus tasks and one documents task. It records a failed validation if the reviewed plan cannot support that composition. A generated plan with wrong routes is not silently rewritten through a private API. Add `--headed` to see the browser. Playwright resolves from a local installation, `PLAYWRIGHT_MODULE`, or this machine's bundled runtime.

`--instrumented` selects the separate `work/fieldnote-instrumented` copy. Native launch sets `LLOYAL_LOCAL=1`, `LLOYAL_DEV=1` and an identity-log path. HTTP launch selects the matching locally built llama-server. The published addon paths are not used as evidence for a local execution: `native-loaded-identity.jsonl` comes from the actual host and hashes its loaded addon and libraries.

## Raw evidence

Each diagnostic directory contains:

- `protocol.json`: frozen parameters, weights/binary hashes, source/patch hashes, workload source hashes and arm definitions.
- `rN-nN-BACKEND/job.json`: exact inputs, expected answers, context/sequence settings and model path.
- `engine-memory.jsonl`: common engine census and allocation receipts.
- `agents.jsonl`: native public trace, including hierarchy, pressure, spawning, prefills and release.
- `native-identity.jsonl`: actual native image/library identity.
- `round-N-task-N.request.json`, `.response.json`, `http-prefix.json`: serialized HTTP messages, server timing/cache receipts and compiled common-prefix tokens.
- `workload.jsonl`, `result.json`, `status.json`: stage boundaries, actual outputs, validity and failures.
- `resources.json`, `system.before.json`, `system.after.json`: per-process RSS, HTTP processing slots, memory/swap, power and thermal observations.
- `worker.log`, `server.log`, `server-launch.json`, `server.props.json`: runtime configuration and diagnostics.
- `summary.json` and `figures/`: regenerable derived results; raw files remain unchanged.

Composed sessions keep the existing host journal/request/media/trace files, per-process `.memory.jsonl` sidecars, the UI driver's passive frame log and screenshots. An automatically completed journey remains `quality: unreviewed` until its outputs and evidence coverage are reviewed.

## Accounting

| Counter | Meaning and limits |
|---|---|
| Occupied attention cells | Distinct used cells in the engine; shared sequence memberships count once |
| Shared cells / sequence references | Physical cells with multiple owners / sum of logical memberships; different units |
| Attention and recurrent bytes | Engine-owned allocations, separately classified; their sum reconciles with context bytes |
| Model + context + compute | Engine buffer allocation; not physical residency or whole-stack RAM |
| Recurrent rows | Qwen's state rows, including rollback allocation; not text tokens |
| Main-process physical footprint | macOS `task_vm_info`; separate from mapped weights and Metal allocation, never added to either |
| RSS by PID | External resident-page observations; shared pages may recur across processes |
| Saved prompt cache | Actual serialized cache payload bytes and restoration/eviction events; the 1 GiB limit is not usage |
| HTTP cached tokens | Backend receipts for work reused; not proof that concurrent slots share physical storage |
| Runtime cells | HDK pressure accounting; cross-check against physical census at stable boundaries |

Physical census is sampled at decode boundaries no more often than 250 ms and at lifecycle/memory operations. Maxima are sampled maxima, not exact allocator high-water marks. Record buffering avoids per-token flushes; no GPU synchronization was added. `observerTotalNs` accounts snapshot collection/serialization/write calls, excluding unrelated cache-event logging and final buffer closure. On/off timings are the independent overhead check.

`cache.restored` records an actual saved-state restoration. The older `cache.load` event in this instrumentation revision means the lookup function returned successfully; it is not by itself a cache hit. Use the request's `cache_n` and `cache.restored` receipts for reuse claims.

Unknown counters stay null. Projector allocations, browser unique physical memory, shared mapped-page attribution and exact device residency are not yet independently itemized. Their absence blocks a whole-stack memory-saving claim. The diagnostic explicitly has no projector or reranker on either path.

## Instrumentation provenance

Isolated local branches live under `instrumentation/lloyal-node`, its `liblloyal` submodule and its matched `llama.cpp` checkout. All use `bench/memory-instrumentation`. Original repositories, their uncommitted files and the frozen Fieldnote reference are preserved.

Reviewable patches and source IDs are in `instrumentation/patches/`. Shared engine measurement code is used by both native and HTTP builds. The addon loader's identity recorder is the only Node binding change. The workload API is unchanged.

```sh
node scripts/build-memory-instrumentation.mjs
```

This rebuilds the existing isolated checkouts and writes a binary/build receipt. It uses Node 24.6.0 headers for the N-API 8 addon and the pinned engine revision. On macOS it selects Metal and the existing local md4c source; on Linux it selects CUDA and requires an explicit `LLOYAL_BENCH_CUDA_ARCH`. `LLOYAL_BENCH_NODE_HEADERS` and `LLOYAL_BENCH_MD4C` can override those dependency locations. CMake otherwise fetches its pinned md4c release. It never resets or rebuilds the user's original checkout. Stop inference before rebuilding.

Before promoting a figure, check all trial gates, unsuccessful attempts, power/thermal observations, output correctness and realized concurrency. Equal reserved memory is a tie even when physical occupancy differs. A lower occupied-cell count is not, by itself, a lower process-memory measurement.

## Linux / CUDA deployment

The Brev checkout is `/data/lloyal-bench` on `lloyal-bench-lg`. Install dependencies on Linux with the committed application lockfiles; macOS `node_modules` and native binaries are not portable. `scripts/bootstrap-linux.sh` also checks the published `linux-x64-cuda` addon before linking the instrumented source build. The pinned native source has stale optional-package lock metadata; bootstrap retains the original/resolved lockfiles and rejects changes to existing dependencies other than the platform addon packages.

The L40S setup uses Node 24.6.0, CUDA toolkit 12.6.85 and architecture 89 for both instrumented builds. Driver 565.57.01 exposes 46,068 MiB total GPU memory through NVML, with a portion reserved by the driver. Use measured available bytes when calculating capacity; the product's nominal 48 GB label is not a free-memory budget. Model, projector and reranker downloads are checked against the same SHA256 hashes used locally. The published binary already detects the GPU; rebuilding is required only to include the common memory census and actual-loaded-image recorder.

```sh
cd /data/lloyal-bench
bash scripts/bootstrap-linux.sh
. setup/environment.sh
node scripts/build-memory-instrumentation.mjs
npm run bench -- memory doctor
npm run bench -- memory run --counts 2 --repeats 1 --rounds 1 --output comparisons/cuda-canary
```

The diagnostic samples device and per-process VRAM through `nvidia-smi`, including temperature, power, utilization and clock observations. It samples host RSS/PSS/private pages through `/proc/PID/smaps_rollup` and records system swap counters separately. These views are not added together. CUDA validation requires positive device allocations for both model and context; a `CUDA_Host` buffer alone is not GPU execution. Keep raw allocation records, process IDs, binary hashes and sampling costs alongside every result. A missing or unavailable counter remains unknown.

The current 1/2/4/8-agent protocol is a portability and measurement check. It does not find the L40S concurrency limit: its fixture, sequence reservation and count validation deliberately retain the original limits. A larger capacity experiment must declare the task set, shared/private token budgets, sequence reservation, device-memory budget and completion deadline before execution, then retain all failures and repeat both sides of each observed boundary. Account for Qwen's recurrent state and rollback allocations independently of attention KV.

The pinned engine defines `LLAMA_MAX_SEQ=256` in `src/llama-cparams.h` and rejects larger per-context sequence ceilings in `llama-context.cpp`. Hitting that bound is a software limit, not measured VRAM exhaustion. Native administrative branches also occupy sequence IDs. Record productive active agents separately from configured sequence IDs and requested/queued work.

### CUDA capacity protocol

The separate capacity command extends the public-API diagnostic to 254 distinct lookup workers. It keeps the original eight-task protocol intact. The two conditions contain 256 and 768 ledger records; a fixed permutation selects distinct targets, and the shared input and each existing task remain unchanged as concurrency grows. Native uses `withSpine`, `agentPool`, `parallel` and a public Effection scope per round. LangGraph uses `StateGraph`, `Send`, `ChatOpenAI` and its ordinary concurrency behavior.

```sh
. setup/environment.sh
node --import tsx src/cli.ts memory capacity --output comparisons/cuda-capacity-v3-2026-10-10
# Same command with --resume retains all completed failures and successes.
node --import tsx src/cli.ts memory capacity --analyze --output comparisons/cuda-capacity-v3-2026-10-10
```

The protocol file and execution sources are written before calibration. Calibration uses eight workers and 262,144 context cells on both arms. Actual formatted HTTP prompt token counts and native shared-text token counts determine a conservative prefix bound, saved before the capacity sweep. Both arms reserve `n + 2` sequence slots, 256 private cells per worker and 2,048 global spare cells. Native's context contains one prefix; the HTTP budget allows a prefix per concurrent worker. These are sufficient-workload allocation budgets, not an equal-context-size experiment. All context settings and measured occupied cells remain visible.

HTTP uses `cache_prompt=true`, `--cache-ram 1024`, and `--kv-unified`. One exact-checked request primes its prefix cache before two parallel rounds. Priming time, output, memory and cache receipts are retained separately; priming is not counted as a productive concurrent worker. Native starts from its public shared spine. The sweep requests 8, 32, 64, 128, 192 and 254 workers. GPU-allocation failures bracket a refinement to within eight workers, followed by three observations at each boundary. A passing 254-worker point is censored by the unchanged engine's sequence ceiling. The 1,800-second per-round deadline is an experimental bound, not an interactive latency target.

Allocation fit and useful capacity have separate gates. A completed allocation trial requires observed target concurrency, both completed rounds, positive GPU allocation evidence and context release. Useful capacity additionally requires all exact answers. Native active-pool traces and sampled HTTP processing slots establish those respective active-worker counts, not simultaneous GPU decoding. Wrong answers, timeouts, refused spawns, context pressure, corrupted telemetry and CUDA allocation failures remain distinct. Quality can be nonmonotonic with worker count, so a largest all-correct observation is not automatically a frontier.

Initial calibration attempts are preserved in `cuda-capacity-2026-10-10` and `cuda-capacity-v2-2026-10-10`. The first HTTP attempt had one wrong lookup in sixteen; the second was interrupted while correcting an undersized calibration context for the longer ledger, before capacity collection. Revision 3 records these changes explicitly. No failed answer was relabeled as a pass and no capacity results were collected under those initial protocols.

The offline `scripts/report_cuda_capacity.py` reads `capacity-summary.json` and produces square Matplotlib PNGs and an HTML report. It plots completed allocations even when their answer gate failed, marks those points, and lists every failed startup separately. A failed allocation's partial VRAM peak is never presented as a low-memory success.

Revision 3 was stopped after discovering an important serving-layout control. The pinned server defaults to separate KV streams when `--parallel` is specified, while the inherited benchmark launch explicitly enabled `--kv-unified`. `scripts/check-cuda-layout.mjs` compares both settings at exactly 32 workers, 34 slots and 322,048 context cells, with the same priming, cache settings and two rounds. Its results are retained in `comparisons/cuda-layout-control-2026-10-10`. Do not attribute a unified-buffer slowdown to HTTP or LangGraph without this control.

The capacity continuation uses the ordinary separate-stream configuration:

```sh
node --import tsx src/cli.ts memory capacity --http-default-layout \
  --output comparisons/cuda-capacity-default-2026-10-10
```

This revision reserves the actual required sequence count: native `n+2` and HTTP `n`. Native retains the same shared-context budget. HTTP allocates `n * ceil256(prefixBound + 256 + 2048/n)` cells, ensuring every fixed slot can hold its entire input and continuation. Prompt caching remains enabled. The common sweep maximum is 254; HTTP can have two additional sequence IDs beyond that tested range, so its result there is a test-range bound. Native reaches the engine ceiling after accounting for its administrative branches. Earlier unified-layout trials, including operator-interrupted attempts, remain separate evidence.

`scripts/run-cuda-suite.sh` runs the remaining capacity matrix, the unchanged four-worker composed Fieldnote UI experiment, analysis and figures sequentially on Brev. The composed experiment retains its earlier explicit unified serving layout and 32,768-cell shared context; it is a separate condition from the capacity experiment. The script writes progress to `setup/cuda-suite/status.json` and retains a nonzero composed exit status for investigation. Use `setsid` or a terminal multiplexer so an SSH disconnect does not interrupt the batch. It never starts both model stacks together.

For manual use of the shared Fieldnote UI, use `npm run start -- --backend fieldnote --instrumented --port 8100 --corpus fixtures/generated/corpus` (or `--backend langgraph`) on the VM. Run only one stack at a time. Connect through `ssh -N -L 8100:127.0.0.1:8100 lloyal-bench-lg` and open `http://127.0.0.1:8100` locally; no public service or additional exposed port is needed. Fixture loading relocates recorded paths and checks the original hashes without regenerating assets. Automated composed journeys require the copied `validation/deliberation-repeat-2026-10-09.json` procedure and an installed browser. For the isolated browser installation on this VM, set `PLAYWRIGHT_MODULE=/data/lloyal-bench/setup/browser/node_modules/playwright` and pass `--browser-channel chromium` to `memory composed`. Browser identity is recorded in the run.

## Results collected on 9 October 2026

The primary sweep is `comparisons/memory-agent-count-2026-10-09`: 24/24 trials passed (three repeats of 1/2/4/8 agents on each backend). At eight agents, median occupied attention cells were 3,697 native versus 26,277 HTTP. Median sampled main-model process physical footprint was approximately 1,510 versus 1,732 MiB. Both reserved 1,092 MiB of context; native reserved more compute memory. These accounting views must remain separate. System snapshots show substantial pre-existing swap and paging during measurement. OS-footprint and timing deltas are exploratory under those conditions; RSS and physical-footprint rankings differ. The direct engine cell census and allocation receipts are the primary memory evidence.

The scoped two-round eight-agent control is `comparisons/memory-scoped-cache-canary-2026-10-09`. All four on/off trials returned all 16 exact answers. HTTP's second round reused 25,824 input tokens and was faster than the native second round. This is a successful cache-on control, not evidence that prefix caching was disabled.

### CUDA timeout audit and final quality review (10 October 2026)

All five `deadline` outcomes in `cuda-capacity-default-2026-10-10` contain the OpenAI client's explicit Node response-header-timeout diagnostic at approximately 300 seconds. The jobs declared 1800 seconds, but their custom fetch capture used Node's independent five-minute header timer and did not set a matching SDK timeout. These observations are **transport-censored**, not GPU exhaustion and not proof that the declared experimental deadline was reached. Original job/result/source files remain unchanged. `scripts/audit_cuda_timeouts.py` records the evidence separately.

The repair installs pinned `undici@8.11.2`, uses its matching `fetch` and `Agent` with 1800-second header/body limits, and sets the ChatOpenAI SDK timeout to the same value. The AbortSignal remains active; retries remain zero. No inference settings or graph/concurrency behavior change. `test/http-transport.test.ts` verifies delayed headers and explicit cancellation. Only the root dependency entry and Undici were added to the existing lockfile.

`scripts/check-cuda-timeout.mjs` records two checks in `cuda-timeout-repair-2026-10-10`: the original 128-worker short ledger and 64-worker long ledger. It copies the exact original job settings, changes only the deadline transport flag, verifies model/addon/server hashes and retains the new execution source. These checks do not re-bisect the full capacity frontier. The original 152/192-worker short-ledger and 80-worker long-ledger attempts remain censored.

The composed pair in `cuda-composed-2026-10-10` has a completed retrospective review in each backend's `quality-review.json`. `scripts/review_cuda_composed.py` retains claim judgments alongside computed answer hashes, source-byte verification and recorded synthesis-prompt equality. This is a non-blind review by the implementing assistant. LangGraph's first answer explains the figure more fully and adds fewer unsupported claims; both preserve the core numbers, omit the grant qualification in final synthesis and answer the three continuation facts correctly. `comparisonEligible` stays false for quality-equivalent performance. Raw execution status files retain their original `unreviewed` state; the derived summary incorporates the later reviews.

Generate the reviewed HTML and figures with `scripts/report_cuda_capacity.py`. The report combines eligible observations from the parent and repair directories, clearly labels original transport-censored failures, links all attempts, and keeps the composed pair separate from the text capacity diagnostic. A finalized report records the limits of the collected evidence; it does not assert a physical capacity ratio when the engine ceiling or uncompleted widths prevent measuring one.

New capacity protocols now use version 5 with `httpDeadlineMatched: true`; the ordinary capacity command supplies the matching transport flag. Existing runs retain their frozen protocol and source guards. Use a fresh output directory for a new experiment rather than resuming a pre-repair protocol with changed workers. The two corrective checks retain the old capacity controller snapshot and explicitly set the repair flag in their jobs, allowing their request/source equality audit to remain exact.

The timeout investigation also records the pinned server's default `cache_idle_slots=true` policy. Starting each task visits idle slots and may serialize their state into the 1 GiB RAM prompt cache. Wide-run logs show repeated save attempts and evictions. This is a configuration-specific latency contributor; no policy-off ablation was performed, and timing is not attributed solely to HTTP or LangGraph. The repaired runs preserve this server policy.
